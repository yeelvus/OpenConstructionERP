> **评估日期**：2026-08-06  
> **代码根**：`/Users/wyattsun/Desktop/code`  
> **数据根**：`settings.DATA_ROOT` → `~/Desktop/邯郸中材/01成本统计`  
> **对照系统**：OpenConstructionERP fork（`yeelvus`，分支 `feature/cn-boq-import-and-ai-tokens`，基线 **v14.6.0**）  
> **结论摘要**：**可以、而且已经能比较方便地做成本分析**——本仓库负责「算与出快照」，OCE 负责「存、查、联、展」。不必二选一。

## 1. 两套体系分别是什么

| | **Desktop/code（本仓库）** | **OpenConstructionERP（OCE）** |
|--|---------------------------|--------------------------------|
| **定位** | 离线 **ETL + 经营分析流水线** | 在线 **ERP / 项目台账 / 看板 UI** |
| **输入** | 各部门 raw Excel/PDF（采购、机具、人工、财务、合同、报公司表…） | 本仓库产出的 std/sum/JSON、或 OCE 内合同/付款 |
| **核心动作** | 清洗 → 标准化 → 按项目 join → 出 master / HTML / `data_latest.json` | 导入快照与台账 → 权限与项目上下文 → React 看板与财务预算 |
| **运行方式** | 本机 Python 脚本，按月/按需跑 | 服务 `8000` + 前端 `5173`（或 Docker `8080`） |
| **真相源** | `01成本统计` 目录树 + 修正规则 | 库表（快照 + finance 预算/付款等） |

```text
各部门 raw Excel
      │
      ▼
┌─────────────────────┐
│  Desktop/code       │  领域 std/sum + master + Z_report
│  (ETL + 分析脚本)    │  尤其：综合成本看板 data_latest.json
└──────────┬──────────┘
           │ 导入 / 挂载
           ▼
┌─────────────────────┐
│  OpenConstructionERP│  组合层 / 项目 Tab / 人工专题 / 财务预算
│  thcc_cost_board +  │  合同台账 / 付款导入 / 5D（工程成本另一维度）
│  finance 导入       │
└─────────────────────┘
```

## 3. 与 OCE 成本方法的对应关系

| 本仓库（code） | OCE 能力 | 对接现状 | 方便程度 |
|----------------|----------|----------|----------|
| `build_unified_cost_dashboard.py` → `data_latest.json` | `oe_thcc_cost_board` 组合层+项目 6 Tab | **已导入可用** | ★★★★★ |
| 人工费 HTML / 汇总 xlsx | `/cost-board/labor` | **已导入可用** | ★★★★★ |
| `2_责任成本_std` | finance 预算行 + 看板 `resp_cost` | **已批量导入** | ★★★★★ |
| `B_财务付款_std` | finance 付款/发票 | **已有 THCC 导入** | ★★★★☆ |
| 分包 sum / 合同汇总 | contracts 主分包台账 | 部分（路径注册/同步） | ★★★☆☆ |
| 采购/机具 sum | costs / 看板 payload 内字段 | 看板快照内已含；独立模块未深接 | ★★★☆☆ |
| master 宽表差异分析 | 无直接等价页 | 仍用本仓库 TXT/HTML 即可 | ★★★★☆（离线） |
| 5D EVM / S 曲线 | `/5d` costmodel | **另一维度**（工程挣值，不是 THCC 经营台账） | 并列使用 |

**判断**：

- 若目标是 **「月度经营会：合同 / 责任成本 / 过程 / 毛利 / 付款」** → **code 出数 + OCE 看板** 已经形成闭环，**方便**。  
- 若目标是 **「BIM/BOQ 挣值、SPI/CPI」** → 用 OCE **5D**，与 code 的经营台账**互补**，不是替代。  
- 若目标是 **「改规则、洗 raw、重跑全公司宽表」** → **必须在 code 仓库做**，OCE 不做 ETL。

## 4. 方便性评分（针对你的实际用法）

| 场景 | 是否方便 | 说明 |
|------|----------|------|
| 每月重跑综合看板并给管理层看 | **方便** | `dashboard unified` → HTML；或导入 OCE 后看 React |
| 在 ERP 里按项目权限查看同一套数 | **方便** | OCE 导入后带项目上下文与权限 |
| 责任成本明细进财务预算 | **方便** | OCE 一键扫 `2_责任成本_std` |
| 付款明细进财务台账 | **方便** | OCE 扫 `B_财务付款_std` |
| 改项目别名后全局一致 | **较方便** | 维护 `project_name_match_db.json`，各脚本共用 |
| 只更新一个领域、不重跑全库 | **中等** | WORKFLOW 已写增量目标，多数脚本仍偏全量 |
| 追溯「这个数是 raw 还是手改」 | **中等偏难** | 部分 corrections，raw 污染问题仍在（见 WORKFLOW） |
| 纯用 OCE 从零重算 THCC 宽表 | **不方便/不推荐** | 缺 code 的领域规则与 master 刮取 |

**综合**：在「**数据已在 01成本统计 目录、按现有脚本月更**」的前提下，**可以很方便地做成本分析**；瓶颈不在「有没有方法」，而在 **raw 质量与是否坚持一键入口 / 导入 OCE**。

## 5. 推荐工作模式（最小摩擦）

### 模式 A — 离线为主（不依赖 OCE）

1. 更新 raw → 领域脚本 → `0_一键运行_成本流程.py`  
2. `dashboard unified` 出 `Z_report/综合成本看板`  
3. 用浏览器打开 `index.html`  

适合：临时分析、无 ERP 登录场景。

### 模式 B — 离线算 + OCE 展（**推荐**）

1. 同模式 A 生成 `data_latest.json`（及责任成本 / 付款 std）  
2. OCE：`/cost-board/import` 一键导入；责任成本/付款在财务页导入  
3. 日常查看、项目跳转、权限、与合同/付款并列 → **全部在 OCE**  

适合：固定团队、多角色、要和项目档案联动。

### 模式 C — 仅 OCE

仅适合：**已经导入过的快照**上做查询与展示；**不能**替代 code 的月度重算。

## 6. 本仓库的优势与短板（相对 OCE 成本方法）

### 优势（保留在 code）

- 完整 **raw→std→sum→master→看板** 链路，领域知识（规格规则、cell 刮取、别名）都在脚本里  
- 输出 **`data_latest.json` 字段与 OCE 模块一一对应**（设计已对齐）  
- `00_分析入口.py` 降低「记不住脚本路径」的成本  
- 与数据目录解耦（`settings.py`），代码可 git、数据可本地

### 短板（OCE 补，或后续改进 code）

| 短板 | 影响 | 建议 |
|------|------|------|
| 增量不彻底 | 月更仍偏全量重跑 | 按 WORKFLOW 推 `--month` / manifest |
| 中央 cell 硬编码 | 模板一变就错 | 模板变更时回归 master |
| HTML 与主题分裂 | 多套看板视觉不统一 | 经营面以 OCE 为准，code 保计算 |
| 无权限/审计 | 本地文件夹谁都能改 | 正式查阅走 OCE |
| 5D 不在本仓库 | 无法做挣值 | 用 OCE `/5d` |

## 7. 对接清单（保持「方便」的最低约定）

1. **编码统一**：项目一律 `THCC-YYYY-NNN`（或 matcher 库可解析的标准名）。  
2. **月更必出**：`Z_report/综合成本看板/data_latest.json`。  
3. **责任成本 std 目录**保持 `3.1_责任成本/2_责任成本_std` 命名与一文件一项目。  
4. **付款 std** 保持 `B_财务付款_std` 文件名含项目编码。  
5. OCE Docker 挂载：`邯郸中材` → `/host/thcc`，与 `settings.DATA_ROOT` 同源。  
6. 合上游版本后 **重启 OCE**，避免侧栏误报版本。
